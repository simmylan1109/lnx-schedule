# lnx 发版手册

写给"以后要发下一个版本的人"。第一次发版前请完整读一遍,之后每次照着「发版流程」走。

---

## 一、先搞懂两条互不相干的版本线

这是最容易搞混、搞混了就是"用户手机上的数据升不上去"的地方。

| | 是什么 | 什么时候涨 | 在哪 |
|---|---|---|---|
| **App 版本** | `versionCode`(整数) / `versionName`(如 `0.1.0`) | **每次发版都涨** | `app/build.gradle.kts` |
| **数据库版本** | `DbVersion.CURRENT`(现在是 3) | **只有表结构变了才涨** | `app/src/main/java/com/lnx/app/core/database/DbVersion.kt` |

两者**不需要**同步涨:完全可以发 `0.1.1` 而数据库还停在 v3;也可以发 `0.2.0` 而数据库才从 v3 升到 v4。

- `versionCode` 系统拿来判断"这个新包是不是同一个 App 的升级" —— 必须比手机上装的那个大,否则装不上。
- 数据库版本是 Room 拿来判断"你这个库的结构是不是我认识的" —— 用户从 v2 装到 v3 的包时,Room 会自动按迁移脚本把库升上去。

## 二、签名密钥(最要紧的一件事)

| | |
|---|---|
| 密钥文件 | `D:\lnx-release\lnx-release.jks`(**在仓库外面**) |
| 别名 | `lnx`,有效期 30 年 |
| 口令 | **只写在 `D:\11lnx\keystore.properties` 里**(随机生成,已 gitignore) |
| 凭据文件 | `D:\11lnx\keystore.properties`(同上) |

**把密钥文件和 keystore.properties 一起备份到网盘。** 丢掉的后果不是"发不了新版"这么简单:
换个密钥签名,系统会认不出新包是同一个 App,手机上的 lnx 只能卸载重装 —— **日程数据会一起消失**。
(数据本身在设置页的「导出」里有 JSON 备份可以救,但那要用户提前导出过。)

### 口令永远不要写进仓库

**这是本手册自己踩过的坑,写下来免得重犯**:M9 第一版手册里把口令明码写进了这张表,
而手册本身是入库的 —— 等于白做了"密钥放仓库外"的那套设计。凡是入库的东西,
等于公开;口令一旦进了 git 历史,再删也还在历史里。

所以现在:口令只存在于 `keystore.properties` 一个地方。要看它,打开那个文件。
真要再写进文档,就写"见 keystore.properties",别抄值。

> **那串旧口令还留在 git 历史里**(提交 `0b71fc2`),这是已知的、故意不处理的:
> 它对应的密钥已经被整个换掉了(见下方),旧密钥文件连这串口令都打不开 ——
> 也就是说,历史里那串字符现在打不开任何东西。要彻底抹掉得重写历史,
> 而那会改动 M9 之后所有提交的哈希;为一把死口令付这个代价不划算。
> **如果将来要把这个仓库推到公开的地方、或接上 CI 的密钥扫描,那时再重写不迟。**

密钥为什么放在仓库外面而不是提交进去:私钥一旦进了 git 历史,再"删掉"也还在历史里。
放外面,即使 `.gitignore` 哪天写漏了也提交不上去。

> 附:`D:\lnx-release\lnx-release-old-unusable.jks` 是第一版密钥,口令在一次命令行操作里
> 被弄坏了(见下方"踩坑"),已换成新密钥。因为当时这个 App 还没发给任何人,
> 换密钥的代价是零。这个文件留着不删,但**不要再用它签名**。

### 踩坑:cmd 会把整行的变量先展开

想在一条命令里"先算一个口令、再用它改密钥",写成
`set P=xxx && keytool … -storepass "%P%"` 是不行的 —— cmd 会在执行前把**整行**的
`%P%` 展开掉,keytool 收到的是空值。凡是"生成一个值、下一步要用它"的活,
用脚本(或分行)做,别塞进一行。

## 三、发版流程

### 1. 改版本号

`app/build.gradle.kts`:

```kotlin
versionCode = 2          // 比上一个发布版大 1
versionName = "0.2.0"   // 人看的版本号,也跟着往上走
```

### 2. 跑全量测试

```
gradlew :app:testDebugUnitTest          # 单测
gradlew :app:connectedDebugAndroidTest  # 仪器测试(会先卸载手机上的 App)
```

两条都必须是绿的。有红的先修,不要带着红发版。

### 3. 打包

```
gradlew :app:assembleRelease
```

产物:`app/build/outputs/apk/release/app-release.apk`

- 体积约 **1.7 MB**(debug 包是 11.6 MB,差在混淆和资源压缩)
- 已混淆(R8)、已压缩资源、已签名
- **不可调试**(`run-as` 进不去),这是对的
- 会跑 `lintVitalRelease`:manifest / 资源 / API 用法上的**错误**会直接让打包失败。
  debug 构建不跑 lint,所以"能跑通的 debug 包"不等于"能发出去的包"。
  (M9 加备份规则时就是它拦下了 `<exclude>` 路径不在 `<include>` 之内。)

### 4. 装机走查(不能跳)

装到真机或模拟器,把下面这些**真的点一遍**。M7/M8/M9 三个里程碑里的真 bug
(设置页透明、备份文件丢版本号、主题头部叠在一起)**全部**是这一步发现的,
380 条测试一条都没报。

- [ ] 冷启动,三页引导从头走完
- [ ] 选主题(含第 4 个「宁静冷色」,要往左滑才看得到)
- [ ] 授通知权限
- [ ] 新建事件:标题、时间、全天开关、重复、提醒、标签、颜色、优先级
- [ ] 日/周/月三视图各翻一遍,事件显示正确
- [ ] 搜索:搜刚才建的那条,点结果能跳到那天并高亮
- [ ] 抽屉:筛选、切主题、设置页
- [ ] 设置页:外观、提醒、通用、数据四段
- [ ] **导出备份** → 能拉起系统分享面板
- [ ] **导入备份** → 能读出"包含 N 个事件"

### 5. 装机给用户

把 `app-release.apk` 传到手机上点击安装。第一次装会提示"来自未知来源",同意即可。

## 四、如果这次要改数据库结构

按顺序做,漏一步就发出去一个"别人手机上升级会崩"的包:

1. 写 `MIGRATION_N_N+1`,SQL 从 `app/schemas/` 下新版本 json 的 `createSql` **逐字抄**(别手写);
2. 加进 `LnxMigrations.ALL`;
3. 把 `DbVersion.CURRENT` 涨到 N+1;
4. 跑一次构建,让 Room 导出 `N+1.json`,**把它提交进仓库**;
5. 在 `MigrationTest` 里加一条"vN 的库能升到最新"。

第 2、3 步漏了 → `MigrationChainTest` 转红;
第 4 步漏了 → 仪器测试里 `MigrationTestHelper` 转红。

⚠️ 只有一种例外允许破坏"数据不丢":明确的取舍,并且要在 SPEC 里写下来。
`fallbackToDestructiveMigration` 是最后手段,当前**故意没有开**。

## 五、已知取舍与没验到的地方

诚实记录,免得以后当成"验过了":

- **R8 规则靠实机验,不靠读规则自证。** `app/proguard-rules.pro` 只补了官方 consumer rules
  盖不到的两处(枚举名会进备份 JSON、备份 DTO 的序列化器)。已验证:引导/选主题/索权/
  编辑/日历/设置/导出/导入在发布包上全部正常,且**旧版本导出的备份能被发布包读回来**。
- **"提醒到点真的弹出通知"这一段没在发布包上验过。** 验证到的:闹钟确实排进了系统
  (`dumpsys alarm` 里有 `REMINDER_CONTINUE`)、权限弹框正常、`ic_notification` 资源
  确实没被资源压缩裁掉。没验到的:通知真的出现在通知栏里。
  要补验:在真机上建一个 5 分钟后开始、提前 5 分钟提醒的事件,等它响。
  (模拟器上要等,不值当。)
- **系统备份/换机迁移规则没实测过**(终审 P2)。`data_extraction_rules.xml` /
  `backup_rules.xml` 只被 `lintVitalRelease` 验过"写得合法",**没有真的备份过、
  也没恢复过**。规则本身是有把握的(database + file 两个域包含,和
  `BackupFileStore` 写 cacheDir 的事实一致),但"手机丢了日程能不能回来"这件事
  目前只是推理,不是证据。
  要补验:`adb shell bmgr backupnow com.lnx.app` → 清数据 → `adb shell bmgr restore com.lnx.app`
  → 看日程和设置是否都在。
- **"Application 启动时就建通知渠道"这一句没有测试覆盖** —— 仪器测试跑的是
  `HiltTestApplication`,不会执行 `LnxApplication`。渠道本身建得出来的部分有测试。
- **不声明 `android:localeConfig`。** 语言由设置页自己的开关管(spec §3.11)。
  再加一份系统级"应用语言"就是同一个设置两个入口,两边会打架。
  代价:Android 13+ 的系统按应用语言列表里不会出现 lnx。
- **引导页第 2 页横向只能看到 3.5 个主题**,第 4 个要往左滑。没有滑动提示,
  第一次用可能以为就 3 个主题。
